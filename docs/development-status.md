These installed files are reference evidence, not verification of the parent's loaded host; this checkout's test SDK is **0.84.4**.

**Unresolved prerequisite:** the examined public extension API does not establish a process-lifetime, non-inheritable identity/state slot that survives extension-runtime replacement. `session_start` and `session_shutdown` expose lifecycle reasons in 1.0.4, but no handover capability or process-instance identifier. The SDK documents that new/resume/fork replace the active `AgentSession` and recreate services, and extension documentation explicitly invalidates old contexts on replacement/reload. `withSession` supplies a fresh context only for a replacement initiated through that command API; it is not a hook covering ordinary user switches or reload. `pi.appendEntry()` is durable session data, not process-local authorization. `pi.events` is an inter-extension communication API, not a documented lifetime store. Neither retained factory closures nor module-cache/event-bus identity may be assumed to survive these boundaries.

A Node-owned `globalThis`/`process` singleton could be separately evaluated, but it is not an established Pi lifecycle/state contract in the examined references. This investigation did not introduce one, mutate environment variables, derive reusable authorization from PID/start-time heuristics, or persist a session-file bearer capability. This is a blocker under the requested supported-host-API requirement, not a claim that a separately specified process-local mechanism is impossible.

### Required design before implementation

- Obtain a documented host-owned identity/handover contract (or explicit review and approval of an alternative process-local state mechanism). It must survive new/resume/fork/reload, distinguish concurrent runtimes where applicable, and disappear on true process exit without being inherited by a child process.
- Keep session binding backward compatible and the first/default explicit setup choice. An instance binding must be a distinct tagged assignment, never `sessionId: null` interpreted as available. Passive startup must require a matching live instance capability plus the canonical project scope; unknown identity must refuse, not silently downgrade to session binding.
- Preserve credentials after exit/release. After true exit, an instance-bound bot requires explicit local selection and transfer confirmation in the next process. Cross-project switches must disconnect and must not extend authority; any return-to-project policy needs an explicit specification.
- Bind every activation to a fresh session/connection generation. Shutdown must retire receipts, buttons, drafts, Stop/file authority and downloads before new-session activation. Old callbacks/queued replies cannot gain authority over the replacement session, even when the bot is unchanged.
- Extend the locked assignment snapshot/CAS, rollback, release, removal, startup retry and ownership monitor consistently. The existing host-local polling lease is still required: exclusion is not permission to claim an instance binding. A transfer must invalidate the previous capability; failed rollback must not resurrect a superseded owner.
- Add mocked tests for both modes, independent processes, every lifecycle reason including fresh extension factories, cross-project switches, cancellation, stale queued replies/uploads, transfer/release/removal/rollback and legacy settings. No instance-following tests or live claims are warranted until the identity prerequisite is resolved.

## Unreleased native `/restart` — refusal-only capability boundary

Native owner/private-chat `/restart` is registered in the menu and help, but **process restart is not enabled**. It is distinct from `/reload` and never enters model input, queues a turn, waits for idle, invokes shutdown, spawns a helper, or mutates a pane. Refusals leave the current Pi usable. Repeated requests cannot arm a later restart. No new dependency or required herdr installation.

Admission checks cover current ready connection/session, host idle/pending work (missing pending API refuses), Telegram receipts not yet begun, downloads, and approved/in-progress package updates. Linux, TUI mode and `HERDR_ENV=1` are necessary hints only, never proof that this process occupies a pane. Background processes can inherit those markers. Stale connection callbacks refuse. No claims are made about peer-extension task cancellation or atomic host admission freezing.

Read-only investigation used installed Pi **0.99.2** extension/CLI/session docs and extension declarations, plus herdr **0.9.1** help, bundled skill and API schema. The loaded session host can differ; version alone does not enable capability. `pane current --current` and `pane process-info` can expose pane identity, shell PID, foreground process group and processes; these would require correlation to the original process identity, not the investigating background process. No live pane data or process argv/environment was dumped.

**Critical unresolved launch guarantee:** supported `herdr agent start NAME --kind pi --pane ID [--timeout MS] -- ARGS...` uses the canonical `pi` command in an existing interactive shell. It has no explicit executable/cwd override or read-only attestation of that shell's command resolution. The process-info schema does not expose aliases/functions/hash/PATH resolution for the shell's next command. Resolving `pi` in a helper or checking the current Pi executable cannot prove that this shell will launch the intended updated ordinary interactive Pi. No private endpoint, guessed flag, shell-input probe, or `pane run` fallback is acceptable. Therefore all otherwise-eligible requests refuse before session inspection or shutdown; no partially armed helper is shipped.

To enable later: prove the original Linux foreground Pi and stable shell/pane identity, the exact saved session file/header/ID and canonical project cwd, and the updated launcher as resolved by the same shell; reject ambiguous launch flags and never replay initial prompts or use `--continue`. Then implement a directly spawned detached helper with no terminal inheritance, bounded readiness and exit deadlines, process-start identity/PID-reuse checks, same-pane occupancy/cwd rechecks, one-shot launch and bounded private diagnostics. Pi's documented `ctx.shutdown(): void` is a request, not an acknowledged exit/cancellation protocol; cancellation/timeouts must disarm relaunch, not leave a helper that restarts after a later unrelated exit. Own-input fencing and idle/pending rechecks do not freeze other host producers. These are **unimplemented prerequisites**, not tested guarantees.

## Contributor checks

In a **terminal**, from the package checkout:

```bash
npm ci
npm run validate
npm audit --audit-level=moderate
npm run pack:check
git diff --check
```

Source testing is an advanced alternative, not beginner installation. Avoid loading both the npm and source copies: inspect enabled resources with terminal `pi config` first. In a controlled source-only setup, terminal `pi -e .` loads this checkout. Keep the process running; reload changes only through deliberate local Pi `/reload`. Do not infer installation, reload, live testing or publication from an automated check.
